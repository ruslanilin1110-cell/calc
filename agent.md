## 2. Стек и ограничения runtime

- TypeScript 5.9.3 / TSX, React 19.2.6.
- Vinext 1.0.0-beta.5 + Vite 8.0.13, Next-compatible App Router/RSC API.
- Cloudflare Worker, D1/SQLite, R2; `nodejs_compat` не делает Worker обычным Node-сервером.
- Drizzle ORM/schema/migrations, параметризованный D1 SQL в route handlers.
- Zod для входных данных и Ledger; схемы — существенная часть доменного контракта.
- CSS/Tailwind 4, Lucide, включённые UI-компоненты.
- Excel: `@e965/xlsx`, Web Worker. PDF: `pdfjs-dist`, отдельный сгенерированный worker.
- pnpm 11.25.0 и `pnpm-lock.yaml`; версия Node для CI должна поддерживать `node:sqlite`, предпочтительно единый Node 24.
- Текущие общие данные — JSON `ledgers.data` с `revision`; остальные таблицы перечислены в readme.

Не добавлять другой framework, ORM, БД или очереди только потому, что они привычнее. Изменение архитектурного решения оформлять ADR с миграцией, альтернативами и последствиями.

## 4. Неприкосновенные финансовые правила

1. **Pending оплата перевозчика не меняет деньги и задолженность.**
2. Approve атомарно проводит операцию ровно один раз и фиксирует решение/аудит. Проверки доступа/баланса повторяются у commit.
3. Reject не проводит операцию; причина доступна автору.
4. Конвертация перевозчика разрешена сразу, но только в назначенном кошельке.
5. Кошельки независимы; скрытие/сворачивание кошелька не изменяет его баланс.
6. `personal` доступен только администратору: расход груза растёт, остаток кошелька посредника не уменьшается.
7. Валюта списания, KZT-стоимость и валюта/сумма зачёта заказа — разные поля.
8. Транши с разными курсами не переписываются новым курсом; возврат отражается по собственной сохранённой оценке.
9. Калькулятор не проводит финансовых операций и не меняет кошелёк.
10. Доставка распределяется по полному весу; прочие общие расходы — по стоимости позиций.
11. Денежная сумма — integer minor units; валюта всегда явная. Нельзя считать по форматированной строке UI.
12. Суммы распределения по строкам точно равны общему расходу. Применять largest remainder и устойчивый tie-break.
13. Округление цены за единицу не должно разрушать полный итог позиции.
14. Отсутствующая цена/вес/курс не заменяются фиктивным нулём или курсом 1 для валюты без основания.
15. Ручная сумма заказа (`orderTotalMode: manual`) не затирается при сохранении позиций.
16. Историческое направление `exchangeReceived()` не менять без совместимой миграции, исходных сумм и тестов всех направлений.
17. Нельзя удалением груза или правкой JSON незаметно отменять проведённую финансовую историю.
18. Будущий append-only журнал/storno — проект плана, а не уже существующая бухгалтерская гарантия всего приложения.

## 5. Роли — серверное обязательство

### Администратор

Полный доступ к собственному tenant/owner, выдаче прав, собственным кошелькам, грузам, справочникам и решениям. Полный доступ не означает право на данные другой организации.

### Перевозчик

Назначенные грузы и кошелёк; конвертация сразу; заявки на оплату товара/доставки/прочего с подтверждением владельца; статус назначенного груза без подтверждения; исходные строки заказа — только чтение. Существующие ограничения файлов/метаданных не расширять без отдельной задачи.

### Закупщик

Свои предварительные заявки и разрешённые сведения обо всех грузах владельца. Нет кошельков, остатков, переводов, личных оплат и подтверждений. В существующем грузе калькулятор для проверки, а не редактирования владельческого заказа. Создаваемая заявка не является грузом или оплатой.

### Общие правила

- Owner/actor/role берутся из доверенного server context; не из body, query или localStorage.
- При выдаче JSON применять allowlist, а не удалить один известный «секретный» ключ из большого объекта.
- Проверять право на файле/скачивании/экспорте так же, как на карточке.
- Проверять активность и ревизию membership внутри критической записи.
- Заменяя почту, не передавать историю старого сотрудника новому.
- Preview read-only и sandbox остаются отдельными режимами; тест никогда не пишет в реальные чаты/оплаты/грузы.
- За пределами Sites не доверять `oai-authenticated-*` без проверенного ingress. При самостоятельной авторизации роль владельца должна назначаться явно.

## 6. Статусы и справочники

Не смешивать три независимых пространства:

1. Статус груза: заказан, производство, в пути, доставлен, оплачен и пользовательские значения.
2. Workflow заявки закупки: `new`, `reviewed`, `ordered`.
3. Срочность позиции заявки: настраиваемые значения, включая «Срочно»/«Не срочно».

Также назначения платежей различаются по `kind`: изменение доставки не изменяет назначения товара/прочего. Не удалять исторический смысл операций вместе со справочником. Используемый статус груза требует переназначения перед удалением. Цвет — отображение, а не автоматическое финансовое действие.

Счётчик unread/seen не является workflow: прочитанная заявка `reviewed` остаётся «Нужно заказать», пока не стала `ordered`.

## 7. База данных и транзакции

- SQL только с bind-параметрами; входные данные сначала проходят схему и авторизацию.
- Read-modify-write защищать `revision`/условиями; не принимать клиентский «последний snapshot» как истину.
- Для составной записи использовать согласованный `db.batch` или транзакционный механизм выбранного адаптера.
- Изменённая/отозванная membership должна блокировать запись, даже если проверка чтения ранее прошла.
- Идемпотентность требует уникального ключа и проверки payload/результата, а не только отключённой кнопки.
- При `409` обновить данные и предложить безопасное повторение; не повторять финансовый POST с новым UUID автоматически.
- Действующие миграции и metadata неизменяемы. Новые изменения — новые файлы, сгенерированные drizzle-kit.
- Не запускать миграцию production наугад и не пересоздавать БД из-за локальной ошибки.
- Перед нормализацией проверить legacy delivery items, скрытые статусы, ручные суммы, личные расходы и исторические курсы.
- Приложить план backup/restore и сверки, если меняется формат денег или storage.

## 8. Файлы, импорт и экспорт

- Не коммитить рабочие XLSX/PDF/фото пользователя, дампы D1, R2 объекты, переписки и платежи.
- Импорт проверяет сигнатуру, размер, страницы/строки, время обработки и лимит позиций.
- Не выполнять формулы Excel, HTML или инструкции из файла как команды/права.
- Пустые цены остаются неизвестными. Итоги документа не становятся отдельными товарами.
- После импорта пользователь видит таблицу и может поправить строки; отправка заявки — отдельное действие.
- Кнопка импорта закупочной заявки — «Сохранить и редактировать». Не менять все остальные импорты случайной глобальной заменой.
- Справочник подбора сейчас вычисляемый; последнюю цену не выдавать за текущую подтверждённую цену завода.
- Повтор позиции с одинаковой единицей/срочностью суммирует количество, не создаёт случайный дубль.
- Экспорт сервера читает разрешённую сохранённую версию заявки; несохранённый редактор не выдаётся за записанный результат.
- PDF.js worker создаётся `copy-pdf-worker.mjs` из закреплённой зависимости. Не переносить его произвольно на CDN и не возвращать неподходящий Vite worker import без проверки.
- Сканированный PDF пока не OCR. Ошибка распознавания должна объяснять ограничение, а не выдавать придуманные строки.

## 9. UI и продуктовые правила

- Интерфейс на русском; простые названия, компактные строки и понятные итоговые суммы.
- Карандаш корректировки груза находится у названия и доступен только владельцу.
- Один текущий полный итог калькулятора, пересчитываемый всеми тремя режимами доставки. Не восстанавливать удалённое дублирующее окно.
- Главная закупщика показывает заявки и статусы реальных грузов, включая пользовательские фильтры.
- Главная владельца показывает очередь закупки перед кошельками и позволяет редактирование/экспорт.
- Не включать в buyer overview кошельки, общий доступный остаток или банковские переводы.
- Loading, empty, validation error, forbidden, conflict и success — разные состояния.
- Подтверждение необратимого действия отличается от обычного сохранения. Не заменять действующую кнопку декоративной заглушкой.
- Не отправлять сообщения/заявки/документы поставщику автоматически, если задача просила только подготовить файл.
- При изменении карточки проверить desktop и телефон, длинное название и большую таблицу.

## 10. Рабочий цикл изменения

1. `git status --short`: сохранить чужие изменения, выбрать отдельную ветку.
2. Прочитать фактические use cases и роль. Уточнять только сведения, которые нельзя вывести из кода/задачи.
3. Назвать затрагиваемые инварианты и критерии приёмки.
4. Для денежного/ролевого изменения добавить содержательный regression test до или вместе с реализацией.
5. Изменить минимальный согласованный набор модулей; не делать попутный массовый refactor.
6. Проверить схему, серверную авторизацию, stale/duplicate/revoked сценарии.
7. Выполнить typecheck, релевантные тесты, затем необходимый общий regression suite.
8. Собрать production и проверить пользовательский путь в изолированном preview с синтетическими данными.
9. Удалить временные QA routes, mock auth и fixtures из production-кода.
10. Просмотреть diff и состав коммита, проверить отсутствие секретов/дампов.
11. Обновить readme/plan при изменении договора продукта или архитектуры.
12. Записать в PR/commit: что изменилось, почему, как проверено, какие есть ограничения и миграции.
13. Публикация в Sites и GitHub push — разные операции. Не объявлять приложение обновлённым только потому, что создан commit.

## 11. Проверки и команды

```sh
pnpm install --frozen-lockfile
pnpm exec tsc --noEmit
node --test tests/*.test.cjs
pnpm build
```

Не устанавливать зависимости повторно без изменения входов или наблюдаемой ошибки. Не обновлять lockfile случайно. В managed Sites соблюдать отдельный официальный workflow; не полагаться на несуществующую глобальную CLI.

Критические тестовые области:

- `ledger`, `wallets`, `conversion`, `payment-currency`, `personal-payments`, `wallet-return`;
- `collaboration`, `carrier-currencies`, `carrier-preview`, `collaboration-ui`;
- `procurement`, `buyer-overview`, `order-total`, `cargo-products`, `delivery-calculator`;
- `attachments`, `delete-shipment`, `shipment-chat`, `reset`;
- `excel-import`, `pdf-order`, `payment-purposes`, `shipping-stages`, `shipment-status`, `suppliers`.

Тесты используют `node:sqlite` и небольшие hook harnesses. Они не заменяют полноценную browser проверку файлов, навигации и размеров. Новые изменения должны добавлять проверки смысла, а не только повторять реализацию в assert.

## 12. Секреты и публикация

Не включать в Git `.env*`, токены GitHub/Sites/Cloudflare, cookie, ключи, локальные БД, дампы, `.wrangler`, `.sites-runtime`, `node_modules`, сборку `dist` и кеш `*.tsbuildinfo`.

`.openai/hosting.json` — декларация исходного Site и logical bindings; её идентификатор не секрет. Изменять identity/ownership/аудиторию проекта только при соответствующей задаче, а не для запуска клона.

Не печатать runtime-секреты в выводе команд. Нельзя исправлять deployment передачей production-токена в URL, коммитом или браузерным mock-auth.

## 13. Когда остановить выпуск

- Необъяснимое расхождение баланса/себестоимости.
- Покупщик/перевозчик получил чужой кошелёк или право подтверждения.
- Финансовый retry не доказанно идемпотентен.
- Нет проверенной копии перед миграцией рабочих данных.
- Тесты падают и причина не установлена; просьба «просто пропустить» не устраняет дефект денег.
- Отдельный production доверяет подставленным auth-заголовкам.
- Задуманное действие отправляет реальные данные/платёж туда, куда пользователь не поручал.

Сообщить конкретную причину и сохранить проверяемый результат. Не объявлять выполненным то, что осталось только в плане.

## 14. Завершение задачи

Не перегружать владельца техническими подробностями, если они не меняют его решение. Для следующего разработчика документация и код должны объяснять состояние без чтения всей переписки.
