# План развития платформы «Мои закупки — Китай»

Версия плана: 23.10.2026. Исходная точка — приложение Sites 53, исходный commit `3879a86cbdf7122d4eb702ec2c60c4a5976c2ae6`.

Это **план создания устойчивой платформы на базе уже работающего приложения**, а не перечень выполненных задач. Текущий статус каждой функции зафиксирован в [readme.md](readme.md). Правила разработки — в [agent.md](agent.md).

## 1. Принцип выполнения

Каждый пункт проходит одинаковый путь:

1. Описать пользовательский сценарий и финансовые/ролевые ограничения.
2. Зафиксировать контракт данных и поведение старых записей.
3. Подготовить безопасный вариант миграции и резервную копию при работе с данными.
4. Реализовать доменную функцию, затем серверный use case, затем интерфейс.
5. Проверить положительный сценарий, отказ в правах, повтор запроса, конфликт и отказ хранилища.
6. Сверить финансовые итоги до/после.
7. Выпустить на staging, выполнить приёмку владельцем, затем production.
8. Измерить результат и обновить документацию/эксплуатационный runbook.

Не выпускать одновременно новую идентификацию, новую БД и новый финансовый алгоритм: иначе невозможно локализовать расхождение.

### Приоритеты

| Приоритет | Что означает |
| --- | --- |
| P0 | Потеря/искажение денег, утечка, невосстановимость, невозможность воспроизвести выпуск |

### Обязательная негативная матрица

- Закупщик получает `403` на кошельки, конвертации, оплату, подтверждение и правку реального заказа.
- Перевозчик не читает чужой груз, баланс другого кошелька, чужую заявку или приватный документ без назначенного права.
- Отключение участника между чтением и commit отменяет запись.
- Участник одной организации не угадывает UUID и не получает данные другой.
- Поддельный email/роль в body либо неподтверждённый заголовок не создают доступ.
- Preview не изменяет данные и не превращается в административную сессию другого пользователя.

### Набор обязательных тестов

- Одобрение дважды, повтор HTTP после timeout, двойной клик.
- Два админа одновременно одобряют одну заявку.
- Две заявки конкурируют за один остаток.
- Переназначен кошелёк/груз, отозван доступ или изменилась валюта заказа перед commit.
- Отказ БД между отдельными шагами; после сбоя нет частичного проведения.
- KZT→USD, KZT→CNY, USD→KZT, CNY→KZT, USD↔CNY с явным направлением курса.
- Частичная оплата, несколько траншей, refund, переплата и ручная поправка суммы заказа.
- Дробные количество/курс, один minor unit, большие допустимые суммы, превышение лимита.

## 15. E13 — Отдельное production-развёртывание и переход с Sites

**Приоритет:** условный: выполнять только если владелец решил менять рабочий хостинг.

### До переключения

1. Поднять staging с новой идентификацией и закрытым доступом.
2. Применить все миграции; проверить происхождение базы и bindings.
3. Импортировать согласованный D1/R2 snapshot с mapping пользователей.
4. Сверить кошельки, оплаты/решения, долги грузов, строки/вес, калькуляции, заявки, документы и чаты.
5. Провести browser приёмку каждого кабинета настоящими тестовыми пользователями.
6. Проверить резервирование, наблюдаемость, secrets и процедуру отката.
7. Получить решение владельца о времени и окне приостановки записи.

### Переключение

1. Включить режим обслуживания записи старой системы.
2. Снять финальную копию и доимпортировать изменения после предыдущего snapshot.
3. Повторить сверку и подписать manifest перехода.
4. Переключить домен/трафик; старую систему оставить read-only.
5. Проверить вход и одну тестовую непроизводственную цепочку без создания реальных банковских переводов.
6. Контролировать ошибки, конфликты и расхождения балансов.

### Откат

- Заранее определить, что делать с записями, уже появившимися в новой системе: обратный mapping/export либо forward-fix.
- Не возвращать трафик на старую writable БД, если новые проведённые операции не перенесены: это создаст два несовместимых учёта.
- Сохранять старую копию и логи перехода до завершения приёмки.

### Gate G13

Владелец, перевозчик и закупщик работают в новом контуре; данные совпадают; второй активной системы проведения оплат нет; проверен restore после переезда.

## 16. Риски и обязательные решения

| Риск | Что сделать до реализации |
| --- | --- |
| Подмена auth-заголовков при отдельном хостинге | Выбрать trusted ingress/проверку сессии; блокировать прямой обход |
| Пересчёт старых FX по новой формуле | Сохранить исходные суммы и направления, golden reconciliation |
| Нормализация потеряла часть полей JSON | Полный mapping, raw snapshot, dry-run и diff отчёт |
| Прочитанная заявка исчезает из закупки | Отделить unread/seen от workflow `ordered` |
| Retry создал вторую оплату/документ | Уникальные ключи, transactional decision/outbox, проверка внешнего id |
| Администратор скачал устаревшую заявку | Export сохранённой/конкретной ревизии, предупреждение о несохранённых изменениях |
| Оценка доставки попала в фактические проводки | Разные типы cost run и отсутствие posting в калькуляторе |
| Документ/чат открыт через чужой UUID | Проверка tenant/назначения при каждом выдаваемом объекте |
| Добавили OCR и приняли неверную цену | Preview, confidence/ошибки и ручное подтверждение |
| Нет содержимого R2 в backup | Manifest объектов, checksum и настоящий restore |
| UI-рефакторинг расширил роль | Серверные policies + negative regression suite |
| Два источника правды при переносе | Одна активная запись, явный момент cutover, план для новых операций |

## 17. Единое определение готовности

Задача готова только когда:

- [ ] Есть принятый пользовательский сценарий и ясные ограничения ролей.
- [ ] Проверены нормальный запрос, недостаточные права, чужая организация, повтор и конфликт.
- [ ] Денежные изменения имеют источник, курс, сумму, валюту, автора и решение/аудит.
- [ ] При отказе не осталось частичного изменения.
- [ ] Миграция и совместимость данных проверены на восстановимой копии.
- [ ] Typecheck, необходимые тесты и production build проходят.
- [ ] Существенный интерфейс проверен на desktop/mobile и пустых/ошибочных состояниях.
- [ ] Секреты и рабочие персональные/финансовые данные не попали в репозиторий.
- [ ] Документация соответствует реально выпущенному поведению.
- [ ] Выпуск имеет commit/version, наблюдаемость и понятный путь восстановления.

Первый практический спринт: E1 (чистый запуск/CI) + E2 (полная копия/restore) + аудит ingress из E3. Новые удобства каталога и интеграций не должны откладывать эти основы.
